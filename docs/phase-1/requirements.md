# 横川AI 公演用ローカルWebアプリ 要件定義書

## 1. 文書概要

### 1.1 目的

本システムは、演劇企画「7号館からの脱出」に登場する「横川AI」を、公演スタッフがリアルタイムに操作できるローカルWebアプリケーションとして実現することを目的とする。

初期版ではAIによる文章生成・会話生成は行わず、**管理画面でスタッフが入力した任意のテキストを、観客向け投影画面へリアルタイム送信し、投影画面側で字幕表示するとともに音声合成（TTS）で読み上げる**ことを中核機能とする。

公演中の利用を前提とするため、機能の多さよりも以下を優先する。

- 操作が直感的であること
- 誤操作しにくいこと
- 通信状態・再生状態が分かること
- インターネット接続なしでも動作できること
- 障害時にすぐ復旧できること
- 投影画面に管理用UIが露出しないこと

---

## 2. システム概要

### 2.1 基本構成

1台のWindows PC上でローカルWebサーバーを起動し、同一PC上で以下の2画面を利用する。

- 管理画面：公演スタッフが操作する画面
- 投影画面：観客に見せる画面

想定URL例：

- `http://localhost:<port>/admin`
- `http://localhost:<port>/display`

将来的には同一LAN上の複数PCから利用できる構成へ拡張できる設計が望ましいが、MVPでは1台のPC上で完結してよい。

### 2.2 基本フロー

1. スタッフが管理画面を開く。
2. 投影画面を別ウィンドウまたは別ブラウザで開き、プロジェクターへ全画面表示する。
3. スタッフが管理画面にテキストを入力する。
4. 「送信」操作を行う。
5. テキストが投影画面へリアルタイム反映される。
6. 投影画面側でTTS読み上げを開始する。
7. 再生状態が管理画面へフィードバックされる。
8. 読み上げ終了後、履歴として管理画面から確認できる。

---

## 3. スコープ

### 3.1 MVPに含める

- 管理画面
- 投影画面
- 任意テキスト入力
- リアルタイム送信
- 投影画面での字幕表示
- TTS読み上げ
- 再生中／待機中などの状態表示
- 読み上げ停止
- 直前発話の再読み上げ
- 入力クリア
- 発話履歴
- 投影画面接続状態表示
- ローカル環境のみでの動作
- 投影画面の全画面運用
- 基本的なエラー処理
- 公演中の再接続・再読み込みへの耐性
- 最低限の設定画面または設定機能

### 3.2 MVPでは含めない

- ChatGPT、Gemini等による自動文章生成
- 自由会話AI
- 音声認識
- 観客の音声入力
- カメラ入力
- 顔認識
- 謎の自動判定
- 自動進行
- 建物設備・実際の施錠装置との接続
- クラウド接続を必須とする機能
- 外部APIが停止すると公演できなくなる構成
- 高度なユーザー認証
- 複数会場の同時運用

## 4. 機能要件

## 4.1 管理画面

### FR-ADM-001 管理画面表示

- `/admin` 等の明確なURLで管理画面を開けること。
- 投影画面とは明確に分離されていること。
- 公演中に必要な操作が1画面内で完結することを基本とする。

### FR-ADM-002 テキスト入力

- 任意の日本語テキストを入力できること。
- 複数行入力に対応すること。
- 長文入力時にもUIが破綻しないこと。
- 通常のEnterは改行として扱うこと。
- キーボードショートカットによる送信を実装する場合、誤送信しにくい組み合わせとすること。
- 推奨：`Ctrl + Enter` または `Cmd + Enter` で送信。

### FR-ADM-003 送信

- 「送信」ボタンを明確に配置すること。
- 送信時に入力内容を投影画面へリアルタイム送信すること。
- 送信後に、少なくとも以下のいずれかが管理画面で確認できること。
  - サーバー受信済み
  - 投影画面受信済み
  - 音声再生開始
  - 音声再生完了

### FR-ADM-004 再生状態表示

管理画面上で、少なくとも以下の状態を識別できること。

- 投影画面未接続
- 投影画面接続済み
- TTS待機中
- TTS再生中
- TTS停止
- エラー

状態は色だけに依存せず、テキストでも判別できること。

### FR-ADM-005 停止

- 現在再生中のTTSを管理画面から即時停止できること。
- 停止してもアプリケーション全体が不整合状態にならないこと。
- 停止後に次の発話を正常に送信できること。

### FR-ADM-006 再読み上げ

- 直前に送信した発話を、ワンクリックまたは簡単な操作で再読み上げできること。
- 再読み上げ時には、履歴上で再生されたことが分かることが望ましい。

### FR-ADM-007 入力クリア

- 入力欄をワンクリックで空にできること。
- 誤操作防止のため、発話履歴までは削除しないこと。

### FR-ADM-008 発話履歴

履歴には最低限以下を保持・表示すること。

- 発話テキスト
- 送信時刻
- 発話IDまたは内部識別子

望ましい機能：

- 履歴から入力欄へ復元
- 履歴から再読み上げ
- 最新履歴が上または下に統一された順序で表示
- 一定件数を超えた場合でも操作性を維持

### FR-ADM-009 プリセット発話

MVPでは必須度は低いが、以下の拡張を容易にできる構造とすること。

- 任意の定型文を登録
- ボタンからすぐ読み上げ
- プリセットの追加・編集・削除

初期版では、プリセット機能を簡易実装してもよいし、将来拡張用としてデータ構造だけ考慮してもよい。

## 4.2 投影画面

### FR-DSP-001 投影画面表示

- `/display` 等の明確なURLで観客向け画面を開けること。
- 管理用ボタン、デバッグ情報、開発者向けUIを表示しないこと。
- 全画面表示に適したレイアウトであること。

### FR-DSP-002 字幕表示

- 管理画面から受信したテキストを投影画面へ表示すること。
- 日本語を読みやすい大きさで表示すること。
- 長文でも画面外にはみ出さず、適切に折り返すこと。
- 観客向けの視認性を優先すること。

### FR-DSP-003 TTS読み上げ

- 受信したテキストを音声合成して再生すること。
- 日本語読み上げに対応すること。
- 同じPC上の音声出力デバイスから再生できること。
- 投影画面側のブラウザリロードによって、直前の音声が勝手に再生されないこと。

### FR-DSP-004 表示状態

- 待機時にも不自然な空白画面にならないことが望ましい。
- 例：
  - `YOKOGAWA AI`
  - 待機アニメーション
  - システムステータス風表示
- ただし初期版では過度な演出は必須としない。

### FR-DSP-005 再接続

- 投影画面をリロードしてもサーバーへ再接続できること。
- 再接続後、現在表示すべきテキストを復元できること。
- ただし再接続だけを理由にTTSを自動再生しないこと。

## 4.3 リアルタイム通信

### FR-RTC-001 双方向通信

以下をリアルタイムにやり取りできること。

管理画面 → 投影画面：

- 発話テキスト
- 読み上げ指示
- 停止指示
- 将来的な表示変更指示

投影画面 → 管理画面：

- 接続状態
- 発話受信
- TTS開始
- TTS終了
- TTSエラー

通信方式は技術選定に委ねるが、WebSocket等のリアルタイム双方向通信に適した方式を推奨する。

### FR-RTC-002 イベント設計

将来拡張を考慮し、通信データはイベントとして扱える設計が望ましい。

例：

```json
{
  "type": "speak",
  "id": "msg-001",
  "text": "プリンキピアについて説明します。"
}
```

将来的に追加しやすいイベント例：

- `speak`
- `stop`
- `clear`
- `set_mode`
- `play_sound`
- `show_image`
- `blackout`

## 4.4 発話キュー

### FR-QUE-001 発話中の追加送信

発話中に次の文章を送信した場合の挙動を明確にすること。

初期仕様では、以下を推奨する。

- 通常送信：現在の発話終了後に再生する
- 停止：現在発話を中断する
- 再送信：必要に応じて現在発話の後ろに追加する

MVP実装で複雑になる場合は、キューを1件以上保持できればよい。

### FR-QUE-002 キュー状態

- 現在再生中の発話が分かること。
- 次に再生予定の発話が存在する場合、それを管理画面で確認できることが望ましい。
- 停止時にキューを残すか破棄するかは実装上明示すること。
- 推奨：停止は現在発話のみ停止し、キュー操作は別操作にする。

## 4.5 TTS

### FR-TTS-001 TTS方式

技術選定は実装者に委ねる。

ただし、以下を満たすこと。

- 日本語読み上げ可能
- ローカル環境で利用可能
- インターネット接続を必須としない
- 本番環境で再現性がある
- セットアップ手順をREADMEへ明記できる

初期MVPではブラウザ標準TTSを利用してもよいが、将来的にVOICEVOX等のローカルTTSへ交換しやすい抽象化を行うことが望ましい。

### FR-TTS-002 音声設定

可能な範囲で以下を設定可能とする。

- 音声
- 話速
- 音量
- ピッチ

利用するTTS方式で未対応の項目がある場合は無理に実装しなくてよい。

### FR-TTS-003 TTS失敗時

- TTS失敗を管理画面に通知すること。
- 字幕表示は継続できること。
- アプリ全体が停止しないこと。
- 再読み上げを試せること。

### FR-SET-001 設定保持

最低限、以下を設定として保持できることが望ましい。

- TTS関連設定
- 字幕表示ON/OFF
- 投影画面表示設定

### FR-SET-002 再起動後

## 5. 非機能要件

## 5.1 対応環境

- 主対象OS：Windows
- 主対象ブラウザ：Google Chrome最新版を想定
- インターネット接続：不要
- 実行環境：ローカルPC
- 投影：HDMI等で接続された外部ディスプレイ／プロジェクター

## 5.2 性能

目標値：

- 管理画面送信から投影画面への文字反映：体感上ほぼ即時
- 目安：100ms〜500ms程度
- TTS開始：実用上待たされないこと
- ローカルTTS生成が必要な場合も数秒以内を目標とする

## 5.3 可用性

- 投影画面を再読み込みしても復旧できること。
- 管理画面を再読み込みしてもサーバーが停止しないこと。
- 投影画面が未接続でも管理画面自体は操作可能であること。
- 投影画面未接続時に送信した場合は警告を表示することが望ましい。
- ネットワークやTTSの一時的障害でアプリ全体がクラッシュしないこと。

## 5.4 操作性

- 公演中に初見のスタッフでも理解できること。
- 重要ボタンは明確に区別すること。
- 停止ボタンはすぐ押せる位置に置くこと。
- 状態表示はテキストでも明示すること。
- 誤送信しやすいUIを避けること。

## 5.5 視認性

投影画面：

- 大画面投影を前提に十分な文字サイズ
- 高いコントラスト
- 長文折り返し
- 管理用要素を表示しない

管理画面：

- 現在状態
- 接続状態
- 発話中テキスト
- 履歴
- 送信操作

が一目で把握できること。

## 5.6 ログ

最低限以下のログを記録できることが望ましい。

- アプリ起動
- 投影画面接続／切断
- 発話送信
- 発話開始
- 発話完了
- 発話停止
- エラー

保存形式は自由。

## 6. 安全・公演運用要件

### SAF-001 実設備との分離

本システムは、実際の以下の設備を操作しない。

- 建物の施錠装置
- 非常口
- 防災設備
- セキュリティ設備
- 電源設備

劇中上の「ロックダウン」「セキュリティ解除」は演出上の表示・音声としてのみ扱う。

### SAF-002 手動代替

TTSが使用不能になった場合でも、字幕表示だけで公演継続できることが望ましい。

### SAF-003 緊急停止

スタッフが即時に音声を止められること。

### SAF-004 復旧

本番中にブラウザまたはアプリを再起動しても、短時間で復帰できること。

## 9. 技術要件

### 9.1 技術選定

具体的なフレームワーク・ライブラリ・言語は実装者に委ねる。

ただし以下を優先すること。

- Windowsでセットアップしやすい
- ローカルで完結する
- 開発・保守が容易
- WebSocket等のリアルタイム通信を扱いやすい
- UI実装が容易
- 将来的なTTS差し替えが容易
- 不必要に複雑なマイクロサービス構成にしない
- 1コマンドまたは少数コマンドで起動可能

### 9.2 推奨アーキテクチャ

以下のような責務分離を推奨する。

```text
Web Server
├─ Admin UI
├─ Display UI
├─ Realtime Event Layer
├─ Speech Queue
├─ TTS Adapter
├─ State Store
└─ Logging
```

TTSは抽象化し、実装を差し替えやすくすることが望ましい。

## 11. Git / GitHub 運用要件

### GIT-001 Git管理

- 開発開始時からGitで管理すること。
- 既存リポジトリがある場合は、その履歴を保持すること。
- リポジトリが存在しない場合は初期化すること。

### GIT-002 こまめなコミット

大きな1コミットにまとめず、意味のある単位でこまめにコミットすること。

例：

1. `chore: initialize project`
2. `feat: add admin and display routes`
3. `feat: add realtime messaging`
4. `feat: add text to speech playback`
5. `feat: add playback controls`
6. `feat: add speech history`
7. `feat: add reconnect handling`
8. `test: add core flow tests`
9. `docs: add setup and operation guide`

### GIT-003 GitHub

- GitHubリモートが設定済みで認証可能な場合は、節目ごとにpushすること。
- 認証や権限がない場合は無理に破壊的操作をせず、ローカルコミットまでは確実に残すこと。
- force pushは原則行わないこと。
- 既存履歴を書き換えないこと。

## 13. 受け入れ条件

以下をすべて満たした時点でMVP完成とする。

1. Windows PC上でローカル起動できる。
2. 管理画面と投影画面を別々に開ける。
3. 管理画面から任意の日本語テキストを入力できる。
4. 送信すると投影画面へ即時表示される。
5. 送信テキストがTTSで読み上げられる。
6. 管理画面で投影画面の接続状態が分かる。
7. 管理画面で読み上げ状態が分かる。
8. 読み上げ途中で停止できる。
9. 直前の発話を再読み上げできる。
10. 発話履歴を確認できる。
11. 投影画面の再読み込み後に再接続できる。
12. 投影画面再読み込みだけでは音声が勝手に再生されない。
13. インターネット接続なしで中核機能が動く。
14. READMEだけを読んでセットアップ・起動・基本操作ができる。
15. 基本フローの自動テストまたは再現可能な検証手順が用意されている。
16. Git履歴が意味のある複数コミットに分かれている。
17. 実装途中の仮画面・TODOだけを残して完成扱いにしない。
18. 公演利用に耐える最低限の例外処理と復旧手段がある。

## 15. 完成後に期待する状態

スタッフは以下だけ理解すれば運用できる状態を目標とする。

1. アプリを起動する。
2. `/admin` を管理用画面として開く。
3. `/display` をプロジェクター側へ全画面表示する。
4. 管理画面に文章を入力する。
5. 送信する。
6. 横川AIが投影画面上で字幕を表示し、その文章を読み上げる。
7. 必要なら停止・再読み上げする。

本システムの初期版では、**AIが何を言うかを自動で考えることよりも、人間が意図したセリフを公演中に確実に・即座に・安全に横川AIとして発話させられること**を最優先とする。
