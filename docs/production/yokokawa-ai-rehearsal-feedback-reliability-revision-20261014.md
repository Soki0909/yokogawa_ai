## 2. P0：通常NEXTを1.5秒の連打防止へ戻す

**採用方針：音声・SE・字幕・有限長演出の「終了受信待ち」をNEXTの必須条件から外す。** 役者と舞台進行を優先し、オペレーターが判断してNEXTを押せること。

- 本番AdminのNEXT、キーボードショートカット、Show UIのすべてで、受理したNEXTの直後から**1,500msだけ**二重入力を無効にする。以降は通信済み終了イベントが欠けていてもNEXTを操作可能にする。
- `src/cue-completion.js` / `src/state-store.js` / `src/server.js` / `public/js/admin.js` の `CUE_NOT_COMPLETE` / `nextBlock` / `cueRun` の使用範囲を監査し、**残存した終了待ちが通常NEXTを塞がない**ことを確認。終了情報は診断・ログのために残してよいが進行の必須ゲートにしない。
- WebSocketの重複送信、キーrepeat、複数Adminでの同一actionId再送、画面再接続による二重実行は受理しない。防止策は1.5秒の完了判定ロックに置き換えるのではなく、**短時間重複排除・actionId冪等性**で構成する。拒否された入力の予約実行や後追い実行は絶対禁止。
- NEXTを前Cueの再生中に押した場合、旧Cueの音声・SE・字幕・遅延中アニメーション／タイマーを安全に無効化して、次Cueを開始する。旧Cueの遅延音声や絵が後から復活しない。
- 音声出力に対する真の NOT READY（素材不足・出力障害）はNEXT終了判定とは別物。映像だけ進み音声が鳴らない事故を作らない。停止／復帰経路を明示し、準備が必要なら分かりやすく示す。
- **STOP / BLACKOUT は常に即時実行可能**。REPLAY / 明示的ジャンプも終了受信待ちで塞がない。
- UIには「次のCue名」「現在のCue」「最後に受理したNEXT」「1.5秒連打保護」を表示し、終了受信欠落による灰色のままのNEXTをなくす。

## 3. P0：音声の冒頭欠け・開始遅延・長時間待機後を解決

- 現候補の `public/js/production-audio-engine.js` は全WAVをPCMにdecodeして再利用する。これは維持し、**実出音が欠ける理由を別途測る**。AudioBufferSourceの`start()`成功、WebAudio内部captureの正常、Context clock進行だけでは**HDMI/Windows/スピーカーから最初の音が出た証明にならない**。
- P-001・P-003・P-020等で、送信／Cue受理／音声スケジュール／PCM波形先頭／WebAudio graph／OS loopback／HDMIスピーカー実出音／映像更新の各時刻を可能な範囲で分離計測。特に**先頭100～500msのエネルギー欠落・ミュート**を比較する。
- HDMI機器・Windowsオーディオの冷間起動、音声デバイス省電力、出力先切替、AudioContextのsuspend/interrupted、初回HACK描画負荷、OS mixer初回の立ち上がり、音声バッファ供給切れ、Admin/Displayのfocusとbackground制御等を仮説として切り分ける。原因不明のまま「キャッシュ済みだから正常」としない。
- 35分超の実時間idleの前後で比較し、**待機後の最初の音だけ**が欠けるかを記録。過去の `Runtime.evaluate timeout` は検証器と本体のどちらの不応答か別途切り分ける。35分試験は引き続き **未完了** であり、確認できなければPASS扱いしない。
- 無音の出力準備・AudioContext維持・必要時の短い無音先行／先頭サンプル保護などは、音の頭欠けを改善した実測証拠があれば採用可。ただし意図しない出音、自動台詞再生、劇中の不自然な固定ラグを増やさない。場当たり的な待ち時間追加だけでは解決と見なさない。
- 変更前後の**実出音**を比較できなければ、改善を「仮説／ソフトウェア側改善」と明確に限定する。

## 4. P0：Admin音声再生のA/B比較、優位なら移行

**Admin移行は可能だが、速さ・安定性は未証明。条件付き採用。** 同一Windows PCでも、Chrome音声の出力先、AudioContext、ページのライフサイクル、WebSocket経路、字幕同期が異なる。Adminページの内部スピーカーへ誤出力してはいけない。

- 比較A：現在のDisplay Audio Masterで再生（Windows音声出力＝本番のHDMI／教室SP）。
- 比較B：Adminを唯一のAudio Masterとして再生、Displayは映像・字幕のみ。同じPC、同じWAV、同じCue、同じ出力デバイス、同じcold/idle条件で比較。
- 指標：NEXT受理→**物理出音先頭**、波形の冒頭欠落、音切れ、映像/字幕との同期、35分idle後、3公演連続、CPU負荷、画面切替／バックグラウンド影響。可能ならOS loopback＋客席の録音／高fps撮影。ソフトウェアのみの比較では物理面の結論を出さない。
- Bが有意に改善し、本番HDMIに正しく一系統で出力でき、操作・字幕・口パク・SE・STOP・BLACKOUT・REPLAY・Reset・復帰が破綻しないことを確認できれば**Admin側へ切り替える**。優位性がない／証拠不足ならDisplay Audio Masterを維持し、改善を別手段で行う。
- Bを試す際はAへ即時戻せる設定／切替手順を用意し、**同じSE・台詞の二重再生は0**。DisplayとAdminに別々のWAV発火が残らないようオーナーを1つにする。Adminの音声有効化はユーザージェスチャー・Audio READYゲートを遵守する。
- 移行は不要な大規模リファクタリングに発展させない。HDMIが用意できない環境ではBを本番採用に確定させない。

## 5. P0：本番Showに明確なCueスキップ／位置移動を追加

既存AdminにはCue一覧の`▶ 実行`と`位置のみ`があるが、**本番Show画面の緊急操作として明確でない**。`src/state-store.js` の `jumpCue()` は指定Cueを「現在位置」に設定し、次のNEXTで**その次**を実行する仕様なので、誤認しやすい。今回の仕様は新たに明示する。

- Show本番画面に**「緊急：Cueを飛ばす／移動」**を設置。現在Cue、次のCue、全Cue番号・名前から移動先を選べる。
- 利用場面を明示：①「現在のCueを中断し、次の未実行Cueを待機」、②「途中のCueを再生せず、指定したCueを**次に実行する位置**へ移動」。単なる`jumpCue(target)`で一つ先へズレないよう、実操作上の意味を固定する。
- 移動操作そのものは**次の音声・SEを自動再生しない**。明示的なNEXT／GOのみで実行。今のCueの音声・SE・古いタイマー／字幕／transitionは適切に取消し、見せるべき残留画面の扱いは明示・安全側にする。
- 現在位置・次にGOするCue・飛ばしたCue番号をAdminへ明確に表示し、誤操作防止の二段階確認または同等の明示確認を設ける。稽古中は素早く扱え、通常NEXTを妨害しない。
- 復旧演出の前提を満たさず途中へジャンプした場合、過去の演出が自動で補完されると思わない。必要ならそのCueの静的状態を安全に整えるが、勝手な音声・映像・脚本上の演技は挿入しない。
- STOP/BLACKOUTからの手動復帰、二重操作・回線再接続・古い応答、意図しない自動進行、スキップ履歴を回帰検証する。
