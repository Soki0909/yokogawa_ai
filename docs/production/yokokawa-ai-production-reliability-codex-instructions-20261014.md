## 1. P0：音声の初回遅延、プツプツ、35分後の再発を根本から調査・修正

### 観測された不具合（実際のユーザー報告）

- 初回再生で音声がプツプツ途切れることがある。
- 映像は先に始まるが、音声が遅れて始まることが多い。
- 35分程度の待機後にも、音声の開始遅延やプツプツが発生する。
- 前回のソフトウェア計測 p95（NEXT→次フレーム19.4ms、`play()`→`playing`13.2ms）と、実際に音が聞こえるまでの時間は異なる。過去178 tests PASSもこの不具合の否定にはならない。

### コード調査の重点（原因は未確定）

- `public/js/audio-preload.js` は現状 `fetch(..., {cache:'force-cache'})` でバイト取得後に捨てている。再生時に `public/js/tts-adapter.js` の `LocalAudioProvider` が `new Audio(url)` を毎回生成して `play()` している。HTTPキャッシュヒット＝デコード・デバイス・初回出音まで準備完了、とはいえない。
- `public/js/lip-sync.js`：`LipSyncController.analyse()` は `createMediaElementSource(audio)` を接続するが、使う `AudioContext` の `state` が `suspended` になっていた場合の明示的 `resume()` 成功待ちがない。長時間待機後・デバイス切替時の状態遷移を検証。
- `public/js/display.js` の `audioOutputPrepared` / `audioReadySent` が、実際の出音準備の有効性を保証しているか。Reset、STOP、reconnect、Windowsオーディオデバイス切替、35分放置で状態が乖離しないか。
- `public/js/cue-sfx.js` のSE系経路と発話経路で準備・再開・ルーティングが異なる。PAとは別経路なのでHDMI出力先を明示確認。
- `audio.onplay`／`playing` は実際のスピーカー出音の証明ではない。`waiting`, `stalled`, `suspend`, `canplaythrough`, `error`, `ended`、`AudioContext.statechange` と画面・音声の発生を紐づけて記録する。
- 負荷、初回デコード、オーディオバッファ、GC、Windows音声デバイス省電力、背景タブ、映像の初回HACK描画（約267ms）が共通原因／独立原因のどちらかを観測する。

### 必須の修正目標

1. **本番前に再生素材の実デコードまで完了**させ、**そのデコード済み音声を実際のCue再生で再利用**する。Web Audio `AudioBuffer` の事前decode＋再生を第一候補に、既存のリップシンク・音声効果・音量調整との整合性、メモリ常駐量、停止／再生の安全性を比較して選ぶ。単に `fetch` のキャッシュを温めるだけでは不十分。音声変更を避け、元WAVは不変（ただし後述の文間調整分の合成は許容）。
2. 初回Cue前に、**音声デバイス・AudioContext・全本番WAV・全必須SE・主要表示素材が本当に使用可能**か確認する明確な `READY` ゲートを実装する。単なる「接続済み」「読み込み開始済み」ではREADYにしない。失敗時は原因が分かる表示、再試行、操作禁止で**fail closed**。
3. 長時間待機で `AudioContext` が `suspended` / `interrupted` / `closed` になった際に安全に再開／再準備する。バックグラウンド監視・必要時の無音準備・本番開始直前の再検証を検討し、勝手な音声や無断Cueは一切流さない。**35分後の最初のGOを遅延・音切れさせない仕組み**にする。単に「開演前に一度再生してください」で終わらせない。ユーザー操作の要求が必要なブラウザ制限はUIに正しく示す。
4. 音声が未準備なら映像だけ先行させず、**同じCueの映像・音声が自然な同期で開始**する。演出として意図された無音、起動音→台詞、ERROR警告→台詞、P-004内HACK、Cue内phaseは維持。音声準備に失敗した際は自動的に遅れて鳴らさず、停止してオペレーターに原因・復帰手段を明示。
5. **録音・光学／音響観測**で、目視・耳で気づく音途切れや映像と出音のズレがないことを検証する。Chrome内部 `play()` イベントだけでは合格としない。測定できない物理遅延は「未計測」と明記。
6. AudioContext、AudioBuffer、画像デコード済みリソース、listeners、timers、WebSocket、Cue履歴のライフサイクルを設計し、無制限増加・メモリリーク・多重再生なし。閉じたContextを再使用しない。

### 失敗・復旧規則

- STOP/BLACKOUTは待機ゲートより常に優先し、即時反映。
- STOP・Reset・別Cue・disconnect・sleep/resume後、**古い音声が遅れて鳴ることは0件**。`generation`/token方式を維持・強化。
- 音声再生失敗を字幕や `onplay` だけで成功扱いしない。オペレーターに分かる `ERROR / NOT READY` とREPLAY、再準備手順を用意。自然発火で勝手に続行・リトライしない。
- セリフとSEの開始順序、字幕typewriter、元WAVの音声特性は維持。

## 2. P0：NEXTを「前のCueの全演出完了」までロック

- 現在は1,200msのNEXT連打防止が主体。ユーザー要望は**演出完了までNEXT不可**。
- 完了条件はCue別に、(a)実際の音声の再生完了、(b)意図したSEの再生完了、(c)そのCueに属する有限長の映像・transition・sequence・ゲージ等の終了、(d)字幕タイムラインの終了、を組み合わせる。**時間だけで音声完了を仮定しない**。
- 謎画像や静止した最終画面など「次Cueまで表示し続ける状態」は、終了待ちに含めない。各Cueで何を「有限長演出」と扱ったか一覧化。演出がなく音声だけのCueは音声完了時に解放。意図した役者待ち・手動GOを自動進行に変えない。
- `src/state-store.js` の `nextCue()` と `src/server.js` の操作受付側で拒否し、**Admin UIだけでなくサーバーでも強制**する。UIは無効化と、理由（「音声再生中」「演出中」「音声未準備」「異常停止」など）を表示。リロードや多重Adminからも突破できない。
- 既存1,200ms連打保護も残す。停止・ブラックアウトは即時可。REPLAYは明示操作で可能。エラー時にtimeoutだけで無条件開放しない。必要なら明示的な運用回復操作を用意し、ログを残す。
- P-V07とP-020は独立Cueを維持し、復旧演出完了後に人間の芝居を挟み、オペレーターの手動GOでP-020。
